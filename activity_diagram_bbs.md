# 1. Назначение

Диаграмма описывает основной алгоритм обработки биллингового события:

1. Получение информации о банковской операции из Kafka topic `transfer.completed`.
2. Проверка входных данных.
3. Проверка события на повторную обработку по `eventId`.
4. Получение тарифа, скидок и лимитов.
5. Расчёт комиссии.
6. Создание и сохранение начисления.
7. Передача комиссии на списание в АБС.
8. Сохранение итогового статуса и публикация результата в Kafka topic `billing.result`.

# 2. Табличное описание шагов

| № | Участник | Шаг | Результат | Обработка ошибки |
|---:|---|---|---|---|
| 1 | Система денежных переводов | Опубликовать событие `TRANSFER_COMPLETED` в Kafka topic `transfer.completed` | Информация о банковской операции передана в Banking Billing System | При ошибке публикации выполняется повторная отправка события |
| 2 | Banking Billing System | Считать событие из `transfer.completed` | Событие поступило на обработку | При технической ошибке событие должно быть обработано повторно |
| 3 | Banking Billing System | Проверить корректность входных данных | Проверены обязательные поля, сумма, валюта и идентификаторы | При ошибке сохраняется статус `INVALID_DATA` в таблицу `billing_event`, результат публикуется в `billing.result` |
| 4 | Banking Billing System | Проверить `eventId` в таблице `billing_event` | Определено, обрабатывалось ли событие ранее | При дубликате новое начисление не создаётся, возвращается ранее сохранённый результат |
| 5 | Banking Billing System / Сервис тарифов | `GET /api/v1/tariffs` — получение применимого тарифа на дату операции | Получены параметры тарифа, действующего для операции | При `HTTP 5xx` или timeout выполняется до трёх попыток |
| 6 | Banking Billing System | Проверить ответ сервиса тарифов | Определено наличие применимого тарифа | При `HTTP 404` формируется `TARIFF_NOT_FOUND`; при `HTTP 5xx` или timeout после повторов — `TECHNICAL_ERROR` |
| 7 | Banking Billing System / Сервис клиентских данных | `GET /api/v1/clients/{clientId}/billing-context` — получение скидок и лимитов клиента | Получены персональные условия расчёта | При `HTTP 404` расчёт продолжается без персональных условий; при `HTTP 5xx` или timeout выполняется до трёх попыток |
| 8 | Banking Billing System | Проверить наличие технической ошибки | Подтверждена возможность продолжения расчёта | При `TECHNICAL_ERROR` статус сохраняется в `billing_event`, результат публикуется в `billing.result`, обработка завершается |
| 9 | Banking Billing System | Проверить наличие тарифа | Подтверждено, что применимый тариф найден | При `TARIFF_NOT_FOUND` статус сохраняется в `billing_event`, результат публикуется в `billing.result`, расчёт комиссии не выполняется |
| 10 | Banking Billing System | Рассчитать комиссию | Получена базовая сумма комиссии | При ошибке расчёта формируется `CALCULATION_ERROR` |
| 11 | Banking Billing System | Применить скидки, лимиты и правила округления | Получена итоговая сумма комиссии | При ошибке применяется сценарий `CALCULATION_ERROR` |
| 12 | Banking Billing System | Сохранить начисление в таблицу `billing_charge` | Начисление и рассчитанная сумма комиссии зафиксированы | При ошибке сохранения требуется повторная обработка |
| 13 | Banking Billing System | Проверить сумму комиссии | Определено, требуется ли фактическое списание | Если комиссия равна 0, устанавливается статус `NO_CHARGE`, обращение в АБС не выполняется |
| 14 | Banking Billing System / АБС | `POST /api/v1/debits` — создание запроса на списание комиссии | АБС проверила счёт и выполнила списание либо вернула бизнес-отказ | При `HTTP 5xx` или timeout выполняется до трёх попыток |
| 15 | Banking Billing System | Обработать ответ АБС | Установлен итоговый статус начисления | `HTTP 200` → `PAID`; `HTTP 422 + INSUFFICIENT_FUNDS` → `PAYMENT_PENDING`; `HTTP 422 + ACCOUNT_BLOCKED / ACCOUNT_CLOSED` → `PAYMENT_REJECTED`; после технических ошибок → `PAYMENT_ERROR` |
| 16 | Banking Billing System | Сохранить итоговый статус в таблицу `billing_charge` | Результат обработки зафиксирован в системе | При ошибке сохранения требуется технический разбор |
| 17 | Banking Billing System | Опубликовать результат в Kafka topic `billing.result` | Итоговый статус и сумма комиссии доступны системе денежных переводов | При ошибке публикации результат должен быть отправлен повторно |
| 18 | Система денежных переводов | Получить итоговый результат | Система получила статус обработки и сумму комиссии | Процесс завершается |

# 3. Основные сценарии ошибок

| Ошибка | Действие системы |
|---|---|
| Некорректные входные данные | Сохранить `INVALID_DATA` в таблицу `billing_event` и опубликовать результат в `billing.result` |
| Повторное событие | Не создавать новое начисление, получить ранее сохранённый результат и повторно опубликовать его в `billing.result` |
| Сервис тарифов недоступен | Выполнить до трёх попыток; после исчерпания попыток сформировать `TECHNICAL_ERROR` |
| Тариф не найден | Сохранить `TARIFF_NOT_FOUND` в таблицу `billing_event`, не выполнять расчёт комиссии и опубликовать результат |
| Сервис клиентских данных вернул `404` | Продолжить расчёт без персональных скидок и лимитов |
| Сервис клиентских данных недоступен | Выполнить до трёх попыток; после исчерпания попыток сформировать `TECHNICAL_ERROR` |
| Ошибка расчёта | Сохранить `CALCULATION_ERROR` в таблицу `billing_event` и завершить обработку без обращения в АБС |
| Ошибка сохранения начисления | Не выполнять списание комиссии до успешного сохранения начисления |
| Комиссия равна 0 | Установить статус `NO_CHARGE`, не обращаться в АБС |
| Недостаточно денежных средств | Установить начислению статус `PAYMENT_PENDING` |
| Счёт заблокирован или закрыт | Установить начислению статус `PAYMENT_REJECTED` |
| АБС вернула `HTTP 5xx` или timeout | Выполнить до трёх попыток, после чего установить `PAYMENT_ERROR` |
| Ошибка передачи результата | Повторно опубликовать результат в Kafka topic `billing.result` |

# 4. Описание значимости артефакта

| Раздел | Содержание |
|---|---|
| Процесс и контекст использования | Артефакт используется при анализе и проектировании процесса расчёта и списания банковской комиссии. Он применяется после подготовки общих требований к Banking Billing System и до детального описания интеграционных контрактов, OpenAPI и AsyncAPI. |
| Цель создания | Показать последовательность работы Banking Billing System, основные точки принятия решений, используемые Kafka-топики и REST endpoint’ы, места сохранения данных и ключевые сценарии обработки ошибок. |
| Что становится определено | Зафиксированы участники процесса, входной топик `transfer.completed`, выходной топик `billing.result`, endpoint’ы получения тарифа и клиентского контекста, endpoint списания комиссии в АБС, таблицы `billing_event` и `billing_charge`, порядок расчёта комиссии и возможные результаты списания. |
| Пользователи артефакта | Системный аналитик использует диаграмму для описания и согласования логики работы системы. Разработчики используют её при реализации интеграций и обработки событий. Тестировщики формируют на её основе позитивные и негативные тестовые сценарии. Заказчик проверяет соответствие процесса бизнес-требованиям. |
| Использование в дальнейшем | На основании диаграммы можно подготовить Sequence Diagram, OpenAPI-описание REST API, AsyncAPI-описание Kafka-событий, модель статусов начисления, тест-кейсы и задачи на разработку. |
| Последствия отсутствия | Без диаграммы участники проекта могут по-разному понимать последовательность расчёта, используемые интеграции, обработку повторных событий, HTTP-кодов и ошибок внешних сервисов. Это может привести к ошибкам реализации, несовместимости компонентов и неполному тестированию. |
