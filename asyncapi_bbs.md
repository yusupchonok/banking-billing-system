# AsyncAPI Banking Billing System

## 1. Назначение

AsyncAPI описывает асинхронное взаимодействие Banking Billing System с системой уведомлений через Kafka.

После изменения итогового состояния начисления BBS формирует событие и регистрирует его в `outbox_event`. `Billing Worker / Event Publisher` публикует событие в Kafka topic `billing.notification-events`.

Система уведомлений подписывается на topic и обрабатывает сообщение независимо от основной биллинговой операции.

---

## 2. Передача событий через Kafka

| Broker | Topic | Producer | Consumer |
|---|---|---|---|
| Kafka | `billing.notification-events` | Banking Billing System | Система уведомлений |

В качестве ключа Kafka-сообщения используется `chargeId`.

Это позволяет сообщениям одного начисления попадать в одну партицию и сохранять порядок обработки в рамках одного `chargeId`.

---

## 3. События

| `eventType` | Когда формируется | Назначение |
|---|---|---|
| `COMMISSION_PAID` | Комиссия успешно списана | Уведомить клиента об успешном списании |
| `COMMISSION_FAILED` | Списание комиссии завершилось ошибкой | Уведомить клиента о проблеме со списанием |
| `COMMISSION_REFUNDED` | Комиссия возвращена клиенту | Уведомить клиента о возврате |

---

## 4. Структура сообщения

```json
{
  "eventId": "88888888-8888-8888-8888-888888888881",
  "eventType": "COMMISSION_PAID",
  "chargeId": "77777777-7777-7777-7777-777777777771",
  "clientId": "11111111-1111-1111-1111-111111111111",
  "amount": 150.00,
  "currency": "RUB",
  "occurredAt": "2026-08-15T10:00:04+03:00",
  "correlationId": "transfer-10001"
}
```

### Поля

| Поле | Тип | Обязательное | Назначение |
|---|---|---:|---|
| `eventId` | UUID | Да | Уникальный идентификатор события |
| `eventType` | string | Да | Тип события |
| `chargeId` | UUID | Да | Идентификатор начисления |
| `clientId` | UUID | Да | Идентификатор клиента |
| `amount` | number | Да | Сумма комиссии или возврата |
| `currency` | string | Да | Код валюты по ISO 4217 |
| `occurredAt` | date-time | Да | Момент возникновения события |
| `correlationId` | string | Да | Идентификатор сквозной трассировки |

Контактные данные клиента в сообщение не передаются. Система уведомлений получает их самостоятельно по `clientId`.

Для событий, возникших из операций системы денежных переводов, поле `correlationId` содержит значение `externalOperationId` исходной операции.

---

## 5. Гарантии доставки

Для публикации используется семантика `at-least-once`.

Это означает, что одно событие может быть доставлено повторно.

Для защиты от повторной обработки:

- каждое сообщение содержит уникальный `eventId`;
- система уведомлений должна выполнять дедупликацию по `eventId`;
- BBS хранит событие в `outbox_event` до успешной публикации;
- при недоступности Kafka публикация повторяется;
- недоступность системы уведомлений не блокирует основную биллинговую операцию.

---

## 6. Transactional Outbox

Изменение бизнес-состояния и создание события должны фиксироваться в одной транзакции PostgreSQL.

Пример:

```text
UPDATE charge
    status = PAID

+

INSERT outbox_event
    event_type = COMMISSION_PAID

COMMIT
```

После этого `Billing Worker / Event Publisher` получает событие со статусом `NEW`, публикует его в Kafka и переводит запись в `PUBLISHED`.

## 7. Описание значимости артефакта

| Раздел | Содержание |
|---|---|
| **Процесс и контекст использования** | Артефакт используется при проектировании асинхронной интеграции Banking Billing System с системой уведомлений через Kafka. |
| **Цель создания** | Зафиксировать канал, структуру события и правила передачи сообщений между producer и consumer. |
| **Что становится определено** | Определены Kafka topic, producer, consumer, типы событий, структура payload, ключ сообщения, correlationId и правила повторной доставки. |
| **Пользователи артефакта** | Системный аналитик использует спецификацию для согласования контракта. Backend-разработчики — для реализации producer и consumer. Тестировщики — для контрактных и интеграционных проверок. |
| **Использование в дальнейшем** | Спецификация используется при реализации Kafka-интеграции, разработке системы уведомлений, настройке producer/consumer и подготовке тестов. |
| **Последствия отсутствия** | Без AsyncAPI producer и consumer могут по-разному трактовать структуру сообщения, типы событий, ключ сообщения и правила повторной обработки. |
